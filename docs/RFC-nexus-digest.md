# RFC: периодический дайджест активных задач в Telegram (SLNexus)

- **Статус:** предложение к реализации
- **Целевая ветка:** `develop`
- **Дата:** 25.09.2026
- **Контекст:** день 18 курса `ai-challenge` — «MCP-инструмент с отложенным или периодическим
  выполнением: сохраняет данные, выполняется по расписанию, возвращает агрегированный результат».
  Результат задания — агент, который работает 24/7 и периодически выдаёт сводку.

---

## 1. Задача

SLNexus сегодня работает как «одна задача за раз»: чтобы понять, что происходит в проекте, надо
открыть трекер. Нужен фоновый режим: бот **сам** присылает сводку по задачам, которые прямо сейчас
в работе, на ревью или на тестировании — что за задача, кто исполнитель, краткое описание,
есть ли обсуждение в комментариях.

- **Когда:** 08:00 и 20:00 по **Asia/Omsk** (UTC+6).
- **Кому:** всем, кто подключён к боту (`ALLOWED_USER_IDS`), одинаковый текст.
- **Тон:** живой, человеческий. Утром — пожелание хорошего дня, вечером — хорошего вечера.
- **Если задач нет:** короткое живое сообщение («всё разобрано»), а не пустой список.

Пример того, что должно приходить (данные реальные, с прода на 25.09.2026):

```
Доброе утро! ☀️ В работе 2 задачи.

🗂 INFRA — «Инфраструктурные задачи»
  • INFRA-4 — Проверка MCP-сервера
    исполнитель: не назначен · приоритет 50 · обсуждений пока нет
    Развёрнут на сервере, создано агентом dsh-term

📱 MOBILE — «Flutter задачи»
  • MOBILE-1 — Реализовать изменение единиц измерения у профиля
    исполнитель: Вячеслав Зюзько · приоритет 50 · 💬 3 комментария
    Последний: «поправил вёрстку, жду ревью»

Хорошего дня! Если что-то застряло — скажи, разберёмся.
```

## 2. Требования

### 2.1. Функциональные

| # | Требование |
|---|---|
| F1 | Раз в сутки в 08:00 и 20:00 по Asia/Omsk всем адресатам уходит сообщение-дайджест |
| F2 | В дайджест попадают задачи только со статусами `in_progress`, `review`, `testing` |
| F3 | По каждой задаче: ключ, заголовок, очередь, исполнитель (имя, не UUID), приоритет, краткое описание, признак обсуждения (число комментариев и, если есть, автор и начало последнего) |
| F4 | Текст зависит от слота: утреннее и вечернее приветствие и пожелание различаются |
| F5 | Пустой список — отдельное короткое сообщение, без «списка из нуля строк» |
| F6 | Расписание и накопленные данные переживают перезапуск контейнера |
| F7 | Недоступность трекера или Telegram не роняет сервис: ошибка в лог, повтор, следующий запуск по расписанию |
| F8 | Ручной запуск дайджеста в любой момент (для проверки и по команде из бота) |

### 2.2. Требования задания (день 18) — форма MCP

| # | Требование |
|---|---|
| M1 | Собрать и агрегировать данные умеет **MCP-инструмент**, а не только внутренняя функция бота |
| M2 | Инструмент **сохраняет данные** на диск (JSON или SQLite) |
| M3 | Инструмент **выполняется по расписанию** (не только по вызову клиента) |
| M4 | Инструмент **возвращает агрегированный результат** (счётчики/дельты/список), а не сырой ответ API |
| M5 | MCP-сервер не зависит от конкретного харнесса: стандартный транспорт, обычные MCP-инструменты |

## 3. Что уже есть (проверено на проде 25.09.2026)

- Трекер `SL Tracker` живёт на том же сервере: `https://tracker.72-56-41-79.sslip.io:8443`,
  API под префиксом `/api`, авторизация `Authorization: Bearer <PAT>`.
- Из контейнера `telegram-bot` трекер по этому публичному адресу **доступен** (`/api/health` → 200).
  Внутренняя сеть трекера (`sl-tracker_default`) к боту **не подключена** — ходить надо по публичному
  адресу (или отдельно присоединять сеть, но это лишняя связанность).
- `zoneinfo.ZoneInfo('Asia/Omsk')` в образе `python:3.11-slim` **работает** (системный tzdata есть),
  дополнительный пакет `tzdata` не нужен. Летнего времени в Омске нет (фиксированный UTC+6).
- Бот смонтирован как `./tg-bot:/app`, то есть файлы данных, положенные рядом с `bot.py`,
  переживают перезапуск и пересборку.
- Адресатов сейчас **3** (`ALLOWED_USER_IDS`), чаты приватные, `chat_id == user_id`.
- HTTP-клиента в `bot.py` нет вообще; `requests` зафиксирован в `requirements.txt`, но не используется.
- Планировщика и хранения подписчиков в боте нет: единственный персистентный слой — `nexus-state`
  в воркере по SSH.

Детали — в приложении `docs/RFC-nexus-digest-appendix.md` (карта `bot.py` по строкам, образцы
ответов API, факты окружения).

> ⚠️ **Прод опережает `develop`.** Боевой `bot.py` — 1396 строк, в `develop` он короче примерно
> на 613 строк; в репозитории пустой `README.md`, а на сервере он на 93 строки. Работу вести
> от **боевого** состояния (оно же у вас локально), а не от текущего `develop`, иначе правки
> лягут в устаревшую базу.

## 4. Архитектура

### 4.1. Вариант А — отдельный сервис `digest-mcp` (рекомендуется)

```
   ┌──────────────────────────────────────────────────────────┐
   │  контейнер nexus-digest-mcp                              │
   │                                                          │
   │  расписание 08:00/20:00 Asia/Omsk (asyncio)              │
   │        │                                                 │
   │        ▼                                                 │
   │  сбор из API трекера ──► снимок (JSONL на volume)        │
   │        │                                                 │
   │        ▼                                                 │
   │  агрегат ──► текст сообщения ──► Telegram sendMessage    │
   │        │                                                 │
   │  MCP-инструменты (Streamable HTTP + stdio):              │
   │    digest_preview · digest_run · digest_history          │
   │    schedule_list · schedule_set · status                 │
   └──────────────────────────────────────────────────────────┘
                    ▲
                    │ MCP (для агентов: dsh-term, Claude Code)
```

- Расписание, хранение и агрегация — **внутри MCP-сервера**, то есть «выполняется по расписанию»
  и «возвращает агрегированный результат» — свойства самого инструмента, а не внешнего крона (M1–M4).
- Рассылку делает тот же сервис, тем же `TELEGRAM_BOT_TOKEN`. Это **не конфликтует** с ботом:
  конфликтуют только два поллера `getUpdates`, а `sendMessage` может вызывать кто угодно.
- `bot.py` почти не трогаем: добавить команду `/digest` (ручной прогон) и пункт в `BOT_COMMANDS`.
  Этого достаточно, чтобы «бот настроен», а риск для его основного цикла — минимальный.
- Сервис читает те же `ALLOWED_USER_IDS`, что и бот, — единый источник адресатов.

### 4.2. Вариант Б — всё внутри `bot.py` (запасной)

Модуль `tg-bot/digest.py` (хранение, сбор, агрегат, рендер) + фоновая asyncio-таска, стартующая
в `post_init`; тонкий MCP-сервер (`tg-bot/digest_mcp.py`, stdio) отдаёт те же функции наружу.
Меньше контейнеров, но планировщик живёт в боте, а MCP-обёртка становится вторичной — по форме
слабее соответствует заданию (M3). Выбирать, только если новый контейнер нежелателен.

### 4.3. Почему не «MCP Tasks» из протокола

В свежих версиях MCP есть экспериментальный механизм Tasks (`tasks/get`, `tasks/list`,
`tasks/cancel`, `tasks/result`) — сервер возвращает хэндл задачи, клиент её опрашивает. В
`@modelcontextprotocol/sdk` 1.30 он присутствует, но наш реальный клиент его не объявляет:
`@deepseek-ai/dsh-mcp-client` инициализируется с пустыми `capabilities`, то есть task-хэндлы
опрашивать не станет. Поэтому опора — на обычные инструменты плюс собственный планировщик;
Tasks можно добавить позже как совместимость для других клиентов, но не как основу.

## 5. MCP-контракт

Транспорт: **Streamable HTTP** (внутри compose-сети, порт наружу **не публикуется**) + **stdio**
(для локального запуска агентом). Авторизация HTTP — обязательный `Authorization: Bearer
<NEXUS_DIGEST_MCP_TOKEN>`, пустой/неверный → 401. Никаких зависимостей от конкретного харнесса.

| Инструмент | Вход | Возврат |
|---|---|---|
| `digest_preview` | `period?: 'since_last' \| '8h' \| '24h' \| '7d'` | агрегат + готовый текст, **без отправки** |
| `digest_run` | `send?: boolean` | собирает снимок сейчас, сохраняет; при `send=true` — рассылает |
| `digest_history` | `limit?: number` | последние снимки и дельты между ними (что появилось, что сменило статус, что закрылось) |
| `schedule_list` | — | расписание, таймзона, последний и следующий запуск |
| `schedule_set` | `times: string[]`, `tz?: string`, `enabled?: boolean` | меняет расписание, сохраняет на диск |
| `status` | — | здоровье: последний прогон, ошибки, доступность трекера, версия схемы данных |

Возврат `digest_preview` (форма фиксирована, чтобы агент мог ей пользоваться):

```json
{
  "generatedAt": "2026-09-25T02:00:03Z",
  "slot": "morning",
  "timezone": "Asia/Omsk",
  "totals": {
    "active": 2,
    "byStatus": { "in_progress": 2, "review": 0, "testing": 0 },
    "byQueue": { "INFRA": 1, "MOBILE": 1 },
    "withComments": 1,
    "unassigned": 1,
    "deltaSincePrev": { "appeared": 1, "statusChanged": 0, "closed": 0 }
  },
  "tasks": [
    {
      "key": "MOBILE-1",
      "title": "Реализовать изменение единиц измерения у профиля",
      "queue": "MOBILE",
      "queueName": "Flutter задачи",
      "status": "in_progress",
      "statusName": "В работе",
      "assignee": "Вячеслав Зюзько",
      "priority": 50,
      "description": "…краткое описание, обрезано до 200 символов…",
```

## 6. Данные

Каталог данных — том (вариант А: `./digest-mcp/data:/data`; вариант Б: `tg-bot/data/`, он уже
переживает перезапуск).

- `state.json` — расписание, таймзона, `last_sent` по слотам, версия схемы;
- `snapshots.jsonl` — по строке на прогон: время, слот, агрегат, задачи (для дельт и истории).

Правила: запись **атомарная** (временный файл + `rename`), ротация по возрасту/размеру
(по умолчанию 90 дней), повреждённый файл не должен ронять сервис — читаем, что можем,
и пишем в лог. Данные — не секреты, но в git им нельзя (`.gitignore`).

## 7. Расписание

- Слоты из `NEXUS_DIGEST_TIMES` (по умолчанию `08:00,20:00`), таймзона `NEXUS_DIGEST_TZ`
  (по умолчанию `Asia/Omsk`).
- Ждём до ближайшего слота, а не «проверяем каждую минуту»: так меньше шума, но обязательно
  переживать сдвиг системных часов (простая защита — пересчитывать не реже раза в минуту).
- **Идемпотентность:** в `state.json` хранится `last_sent` по каждому слоту за дату. Повторный
  запуск контейнера в тот же слот не должен слать второй раз.
- **Пропущенный слот** (контейнер лежал в 08:00): если опоздание меньше часа — отправить,
  иначе пропустить и записать в лог. Порог — конфигом, по умолчанию час.
- Ручной прогон (`digest_run` / команда `/digest`) на `last_sent` не влияет.

## 8. Формат сообщения

- Слот задаёт приветствие и пожелание: 08:00 — «Доброе утро» + пожелание хорошего дня,
  20:00 — «Добрый вечер» + пожелание хорошего вечера. Формулировки — из набора вариантов,
  чтобы текст не выглядел штампованным каждый день.
- Разметка `parse_mode="HTML"`, **все** значения из API — через `html.escape` (в заголовках и
  описаниях встречаются `&`, `<`, кавычки).
- Длинный текст — разбивать по 4000 символов (в боте уже есть такой приём).
- Живость: вводная строка с числом задач, группировка по очередям, человеческие пометки
  («исполнитель не назначен», «обсуждений пока нет»), закрывающая строка. Никаких «список
  задач: 1) 2)» и пустых заголовков.
- Опционально `NEXUS_DIGEST_LLM=1` — доводка текста через воркер (`claude -p`) для более
  живого тона. Обязательно с фолбэком: если воркер занят (`_is_busy()`) или ответа нет за N секунд,
  уходит шаблонный текст. По умолчанию **выключено**: шаблон бесплатный и предсказуемый,
  а включение — осознанное решение владельца.

## 9. Конфигурация

Добавить в `.env` и `.env.example` (в compose — без `:?`, чтобы отсутствие переменной не ломало
весь стек; это уже проходили в соседнем проекте):

```ini
# ─── Дайджест активных задач (SLNexus) ─────────
# Трекер: публичный адрес (из контейнера внутренняя сеть трекера недоступна)
SL_TRACKER_API_URL=https://tracker.72-56-41-79.sslip.io:8443
# PAT участника трекера, права на чтение. Выпускается в UI: профиль → Доступ → Токены доступа
SL_TRACKER_TOKEN=
SL_TRACKER_PROJECT=sweet-limit
# Пусто — взять все очереди проекта
NEXUS_DIGEST_QUEUES=INFRA,MOBILE
NEXUS_DIGEST_STATUSES=in_progress,review,testing
NEXUS_DIGEST_TIMES=08:00,20:00
NEXUS_DIGEST_TZ=Asia/Omsk
NEXUS_DIGEST_MAX_TASKS=30
NEXUS_DIGEST_LATE_LIMIT_MIN=60
NEXUS_DIGEST_LLM=0
# Токен для доступа агентов к MCP-серверу по HTTP (openssl rand -hex 32)
NEXUS_DIGEST_MCP_TOKEN=
```

Сервис **не стартует** с пустым `SL_TRACKER_TOKEN`, если дайджест включён: в логе должно быть
точное имя переменной и где её взять. Тихо неработающий дайджест хуже падения.

## 10. Контракт с SL Tracker

Базовый адрес — `SL_TRACKER_API_URL`, все запросы с `Authorization: Bearer <SL_TRACKER_TOKEN>`.
Ответы проверены на проде; сырые образцы — в приложении.

| Что | Запрос | Что берём |
|---|---|---|
| Очереди проекта | `GET /api/projects/{slug}/queues` | `items[].key`, `items[].name` |
| Список статусов | `GET /api/queues/{key}/statuses` | `items[].key/name/category` (нужен для имён статусов) |
| Активные задачи | `GET /api/queues/{key}/issues?status=in_progress,review,testing&limit=…` | `items[].key/title/status/priority/assignee`; **описания в списке нет** |
| Описание задачи | `GET /api/issues/{key}` | `description`, `queue`, `project`, `assignee`, `author`, `updatedAt` |
| Обсуждение | `GET /api/issues/{key}/comments?limit=1` | `total` + последний комментарий (`items[0].author/body`) |
| Проверка токена | `GET /api/me` | `displayName`, `session.expiresAt` — удобно для `status` |

Особенности, которые надо учесть:

- в списке `assignee` — **объект** `{id, displayName, avatarUrl}` или `null`, поэтому имя
  исполнителя доступно без дополнительных запросов;
- `description` в списке **отсутствует** — на каждую задачу нужен отдельный `GET /api/issues/{key}`.
  Отсюда `NEXUS_DIGEST_MAX_TASKS` (по умолчанию 30) и последовательные запросы с общим таймаутом;
- в `review` и `testing` поле `category` равно `in_progress` — фильтровать надо по `key`, а не по
  `category`;
- статусы в проде: `open` = Открыт, `in_progress` = В работе, `review` = Ревью,
  `testing` = Тестирование, `closed` = Закрыт;
- фильтр `status=in_progress,review,testing` работает (проверено: вернул задачи, `total` корректен);
- пагинация — `nextCursor`; для дайджеста достаточно первой страницы с `limit`.

**HTTP-клиент:** использовать асинхронный (`httpx`, он уже приходит транзитивно с
`python-telegram-bot`) или уводить синхронный `requests` в поток. Синхронный вызов прямо в
асинхронном коде заблокирует обработку сообщений бота — при `concurrent_updates=False` это
остановит весь бот на время запроса.

## 11. Предохранители и безопасность

1. **Токен в логах (найдено на проде).** Контейнер `telegram-bot` логирует каждый `getUpdates`
   вместе с URL, а в URL — токен бота; он сейчас лежит в логах. Лечится явным понижением уровня:
   `logging.getLogger("httpx").setLevel(logging.WARNING)` (и то же для `telegram.ext` при
   необходимости) — сделать это **до** добавления HTTP-клиента, иначе дайджест добавит ещё один
   поток таких логов. Токен бота после этого стоит перевыпустить у BotFather.
2. Секреты — только в `.env` (он в `.gitignore`), в репозиторий не попадают; в логи не пишем
   ни `SL_TRACKER_TOKEN`, ни заголовки запросов.
3. PAT даёт права владельца — дайджесту нужен только чтение: никаких `POST`/`PATCH`.
4. Ошибка одного адресата не должна мешать остальным: рассылка — цикл с `try/except` на каждого
   (в боте уже есть такой образец).
5. Ограничение `NEXUS_DIGEST_MAX_TASKS` защищает и трекер, и длину сообщения.

## 12. Приёмка

| # | Критерий | Как проверить |
|---|---|---|
| A1 | В 08:00 и 20:00 Asia/Omsk приходит сообщение всем адресатам | принудительный прогон + проверка расчёта ближайшего слота тестом на фиксированном времени |
| A2 | В тексте только активные статусы, с исполнителем, описанием и признаком обсуждения | `digest_preview` на проде: сверить с трекером глазами |
| A3 | Утренний и вечерний текст различаются | `digest_preview` при подмене слота |
| A4 | Нет активных задач → короткое живое сообщение | временно сузить фильтр до несуществующего статуса |
| A5 | Данные и расписание переживают перезапуск | `docker compose restart`, затем `schedule_list` и `digest_history` |
| A6 | Повторный старт в тот же слот не шлёт второй раз | перезапуск контейнера после отправки, в логе — «слот уже отправлен» |
| A7 | Трекер недоступен → ошибка в лог, сервис жив | подменить `SL_TRACKER_API_URL` на нерабочий, посмотреть `status` |
| A8 | Сообщение не ломает разметку и длину | задача с `<`, `&`, длинным описанием и 50+ задачами |
| A9 | MCP-инструменты доступны клиенту | вызов `tools/list` и `digest_preview` из стороннего MCP-клиента (например, из `dsh-term` командой `--mcp-check`) |
| A10 | В логах нет токенов | `grep` по логам на `bot` + фрагмент токена |

## 14. Границы (что не делать)

- Не отправлять дайджест в общий чат, если он появится: только приватные чаты адресатов.
- Не менять статусы, не комментировать задачи из дайджеста — только чтение.
- Не тащить метрики сервера (диск/RAM/контейнеры): из контейнера они не видны, а костыль
  с монтированием `/` в этой задаче не нужен.
- Не плодить второй поллер `getUpdates` — Telegram разрешает только один на токен.
- Не коммитить файлы данных и `.env`.

## 15. Открытые вопросы

1. **Очереди:** обе (`INFRA`, `MOBILE`) или все очереди проекта? В RFC по умолчанию — весь проект,
   `NEXUS_DIGEST_QUEUES` сужает.
2. **Живость:** устраивает ли шаблон с вариативными приветствиями, или сразу включаем
   `NEXUS_DIGEST_LLM=1` (доводка через воркер, зависит от его занятости)?
3. **Список адресатов:** сейчас это `ALLOWED_USER_IDS`; если дайджест должен уходить не всем,
   понадобится отдельная переменная или хранилище подписчиков.
4. **Sync репозитория:** этот PR — только документация. Синхронизацию `develop` с боевым
   состоянием (в `bot.py` ~613 строк, пустой `README.md`) стоит сделать отдельным PR до или после.
